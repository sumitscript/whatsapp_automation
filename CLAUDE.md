# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A self-hosted WhatsApp auto-responder (v2):
- **Gateway** (Node, `whatsapp-web.js`): runs the WhatsApp session and the web console.
- **Worker** (Node): answers messages using **vectorless RAG** (BM25F over markdown sections) and a local Ollama LLM.

The bot is **eSumit**, the owner's AI twin, speaking in first person. It only replies inside a **session**: `/hi` starts one and `/bye` ends it. Both are case-insensitive and configurable via `startCommands`/`stopCommands`. Idle sessions time out. There is no number whitelisting.

The two talk over Kafka or Redis Streams. Postgres stores everything permanently. Redis holds chat memory, the cache and the live logs. The deploy target is a single CPU-only 8 vCPU / 32 GB KVM running Docker Compose.

**Owner preference:** do not install or download dependencies on the dev machine (`npm install`, `pip install`, model pulls). Declare them in `package.json` and let CI/Docker install them. Everything that can be verified without deps uses only Node built-ins.

Detailed docs: `docs/ARCHITECTURE.md` (design), `docs/DEPLOYMENT.md` (step-by-step deploy and ops), `docs/RESOURCES.md` (resource budget and dependencies). Knowledge-base sections are written in first person as Sumit.

## Architecture

**Message flow:**
1. `gateway/whatsapp.js` (state machine; the QR is pushed as a data URL) receives the message.
2. `gateway/inbox.js` saves it to Postgres and applies reply policy:
   - checks `replyMode`, block, groups (reply only when mentioned) and rate limit;
   - handles commands via `brain/commands.js`. Start/stop change session state even when the chat is paused; welcome, goodbye and help are instant templates;
   - in `session` mode requires an open session (`gateway/sessions.js`: Postgres `sessions` table plus a cache; one open session per chat; idle sweeper);
   - then checks per-chat pause and the owner takeover key.
   Session side effects (summarize job, `chat:update`) live in the `sessions.on('end')` listener, so `/bye`, console and timeout endings behave the same.
3. Inbox debounces bursts per chat, sends seen + typing, and publishes a job to `wa.inbound` (keyed by chatId).
4. `worker/index.js` runs jobs in a per-chat `KeyedQueue` (keeps order) behind a `Semaphore` (`LLM_CONCURRENCY`), then calls `brain/pipeline.js`.
5. The pipeline streams bubbles back on `wa.outbound`. Inbox delivers them in order through its own per-chat lanes, keeps typing alive and saves each bubble. It drops bubbles whose session ended mid-generation.

**Memory (two levels):**
- **Short-term:** raw turns in a Redis list (`createRedisMemory`, capped at 80).
- **Long-term:** `contacts.memory` notes in Postgres.
- **Folding:** after a reply, if stored turns exceed `historyTurns + 8`, or when a session ends (`summarize` job on `wa.inbound`), the worker queues a fold: `brain.summarize` merges the oldest turns into the notes, then `trimOldest`. The fold queue only drains when `inFlight === 0`, so summaries never delay a live reply.

**Reply pipeline (`brain/pipeline.js`):**
- `resolveIntent` (regex `classifyIntent` plus inheritance) picks an `INTENT_PROFILES` entry. Short follow-ups ("one more", "why?") inherit the previous user turn's intent, and tiny `general` messages never use the KB. Without this a 3B model drifts onto random KB facts. The entry sets: temperature, token scale, and whether to use the KB (`true`, `false`, or `'auto'` = only if `topScore ≥ 1.6×minScore`).
- `detectLanguage` produces the "(Reply in X.)" hint. Follow-ups reuse the previous user turn as the retrieval query.
- **Context window:** `selectHistory` keeps the newest turns within `min(historyTokens, numCtx − system − final turn − maxTokens − 256)` and `historyTurns` messages. It starts on a user turn and merges same-role runs.
- The final user turn carries `[My facts — about <owner>, the one replying (me). Not about <name>]`, `[Notes about <name> — the person I'm chatting with. Their life, not mine]`, `[I'm chatting with]`, then `Their message:` and the language hint. These blocks sit in the *user* role, where "me/my" reads as the user, so every label states whose information it is (with "[Facts about me]" the model credited the owner's projects to the contact and retold the contact's life as its own). The persona prompt refers to "My facts" and "Notes about", so keep them in sync.
- `creative` intent (story, kahani, poem, shayari, horror…) gets no KB facts and no notes, temperature 0.95 and a larger budget; "your story" / "how you built X" stays `about_owner`. "N words" requests raise `maxTokens` (`requestedWords`).
- `selectHistory` shortens old long turns with `compactTurn` (head + tail, deterministic so Ollama's prefix cache survives); the newest turn stays whole. This keeps prompt evaluation fast after long stories or code.
- `summarize` always keeps a stated language preference as `- Prefers <Language>` in the notes.
- Short replies ("yes", "ok", "haan") get `[What I said last]` (the previous assistant turn) next to them so a small model continues that offer instead of an older topic. Long-term notes are only injected when the chat is fresh (< 6 stored turns) or the message refers to the past; mid-conversation they pulled models back to old topics. If generation stops on `doneReason: 'length'`, the last bubble is cut back to a full sentence (`trimDangling`).
- The final user turn ends with a `(…)` rules line built per message: no facts → "don't mention my job/projects/life" (stops invented employers); past reference ("last time", "I told you") → use the notes or admit there are none; "not sure / correct answer" → answer first; previous reply ended in "?" → don't end with another. `test/conversation-qa.test.js` pins these.
- Reply language comes from `replyLanguage` (`brain/lang.js`): a stated preference ("I prefer Hinglish", or "Prefers Hinglish" in the notes) beats a Latin-script message; native scripts always win; an English line inside a Hinglish chat stays Hinglish.
- About-me intent needs a profile topic (typo-tolerant, `PROFILE_WORDS` + OSA `editDistance`) plus "your/tumhara" or a short/neutral message; "my/mera/I" means it's about them ("tum meri help karo" stays general).
- `settings.persona` empty means the built-in `DEFAULT_PERSONA`, so prompt improvements ship with updates. A saved custom persona overrides it.
- KB notes go into the **last user turn**, not the system prompt, so the system prompt + history prefix stays stable for Ollama's prompt cache.
- Chat memory in Redis stores raw text only, never the notes.
- Answer cache only for standalone `about_owner` questions that had KB hits. Its key includes `kb.version` and a hash of the rendered persona, so KB or persona edits invalidate it.
- `MessageChunker` (`brain/format.js`) turns the stream into WhatsApp-formatted bubbles. It never splits inside a code fence and caps at `maxBubbles`.

**Retrieval (`rag/kb.js`, `rag/bm25.js`, `rag/text.js`):**
- Each H2/H3 is a section (an H1 summary becomes a section too). Fields: title = heading + parent ×3, tags = doc title/tags/aliases ×2, body ×1.
- Files starting with `_`, `README.md`, and fenced-code headings are ignored.
- Query expansion via `knowledge_base/synonyms.json` (weight 0.6, bigram keys supported). Typo fixes via bounded edit distance (weight 0.8).
- Selection: score ≥ max(`KB_MIN_SCORE`, 0.35×top), up to `KB_TOP_K`, within the `KB_MAX_CONTEXT_TOKENS` budget.
- When changing tokenizer or stopword rules, rerun `kb:search` on a few real questions. The thresholds were calibrated on the current KB.

**Cross-process state:**
- **Settings:** stored in Postgres (`settings` key/value jsonb), validated by `core/settings-schema.js`. Every process caches them and reloads on the Redis `ch:settings` pub/sub. A new setting must be added to `DEFAULT_SETTINGS` **and** `RULES` there, or it is rejected.
- **KB edits:** made through the API, which writes the file, reloads it and publishes `ch:kb`. Both processes also `fs.watch` the directory.
- **LLM status:** the worker writes a heartbeat to Redis `worker:status` (every 5 s, 20 s TTL). `GET /api/llm/status` merges it with live Ollama `/api/version`, `/api/tags` and `/api/ps` for the dashboard card.
- **Agenda:** the worker spots commitments ("let's meet tomorrow at 5", "remind me to…") and stores them in `agenda_items`. `brain/agenda.js` (pure) gates messages with `looksLikeCommitment`, and `brain.extractAgenda` asks the LLM for kind/title/details as JSON. **Dates are read by `parseWhen` with Intl in `settings.timezone`, never by the model** (a 3B model is unreliable at date math). Extraction runs on the worker's idle queue, ahead of memory folds, and never delays a live reply. If the model fails, `heuristicItem` still records a plain "let's meet tomorrow at 5pm". `sameItem` merges refinements ("make it 6pm") into the existing item. The worker publishes `{type:'agenda'}` on `wa.outbound`; inbox emits `agenda:update` and WhatsApps the owner (`notifyOwner`). The reply prompt also gets a rule not to agree to meetings for the owner. Console: `/api/agenda` + `public/js/views/agenda.js`; confirming/declining can message the contact (`notify: true`).
- **Meetings in any language:** `agenda.js` `normalizeTimeText` folds Hindi/Marathi (Devanagari) and Gujarati words and digits plus Hinglish spellings into Latin tokens before every gate and `parseWhen` ("कल सुबह ६ बजे", "kal sadhe paanch baje", "in 2 hours", "5 to 6pm", "this weekend", "on the 20th"); `guessLocation` reads "station pe" too. Names that look like words ("Ravi", "Tom") are deliberately not mapped. A meeting request (`isMeetingRequest`, or a time-only follow-up after "I want to meet") gets an instant template from `brain/invite.js` `meetingAck` in their language (for every intent except coding/creative/math/joke: naming the owner classifies as about_owner; a bare hour after a day word, "tomorrow 3", reads as 3 pm); "remind him / tell Sumit / unhe bol dena" (`isPassOnRequest`) gets `passOnAck` (noted, passed on, nothing promised; intent `pass_on`) (en, hi-Latn, hi, mr, gu; other languages get English) with **no model call**; it never agrees for the owner, and the worker still files the request in the Agenda. Setting `meetingAck`. When the owner confirms an appointment in the console (`PATCH /api/agenda/:id`, `notify` defaults on via `agendaConfirm`), `inbox.notifyAgendaDecision` sends a localized confirmation with a generated invitation card (`agendaCard`): `invite.js` `invitationData` + `invitationHtml` (pure, flat colours, accent and decoration seeded from the item so every card differs, no external resources) rendered to PNG by `WhatsAppManager.renderHtml` in a throw-away tab of the WhatsApp Chromium (Noto fonts cover the Indic scripts). If rendering fails the confirmation goes out as text. `GET /api/agenda/:id/card.png` previews, `POST /api/agenda/:id/send-card` sends on demand. Tests: `test/meeting.test.js`.
- **Owner answers agenda requests from their own WhatsApp (`brain/owner-commands.js`, `inbox.#ownerCommand`):** every agenda item has a number (its id, shown as `#12` in the console and in the owner notice). A new request (and a refinement of one still pending, `changed` flag from the worker) is sent to the owner's own chat by `ownerNotice` ("Reply *ok 12* to confirm… or *no 12*"; the notice's WhatsApp message id is stored in Redis `agenda:msg:<id>` for 14 days so a quote-reply with just "ok" resolves). The owner replies `ok 12`, `12 yes`, `confirm 3 5`, `no 7`, `done 4`, `ok all`, `pending`, `help` (English, Hinglish, Hindi, Gujarati words; `parseOwnerCommand` only accepts short messages made of command words, numbers and filler, so ordinary notes to self are untouched). `resolveDecision`: explicit numbers win; a bare "ok" applies to the quoted notice or to the only pending item; with several pending it asks for the number; with none it is ignored. Only `fromMe` messages in the self chat count (nobody else can send as the owner); the same message arriving as `message` and `message_create` is acted on once (Redis `ownercmd:<id>` NX). `inbox.decideAgenda` sets the status and calls `notifyAgendaDecision`, shared with the console's PATCH. Confirming ANY item (meeting or to-do) sends the requester a localized confirmation **with a generated card** (to-dos read TASK / Handled by); if the card cannot be drawn or sent the text still goes out. Tests: \`test/owner-commands.test.js\`.
- **Bursts of requests (nothing promised is lost):** the template reply says "noted and passed on", so the request must reach the Agenda. A complete, free request (time known) travels in the reply's done-meta as `meeting: { dueAt, dueText, place, kind }` and the worker files it immediately from `meetingDraft` (no model, no queue, no quiet-gap wait). Everything else that may hold a commitment goes into `agendaQueue`, now an array with one entry per message (it was one slot per chat, so 30 messages in two minutes left one item) carrying the conversation snapshot at that moment, capped at 300. `sameItem` no longer merges two requests of one person by title alone: a time within 2 h is the same request, any other time is a new item unless the message is a refinement (`looksLikeRefinement`: "make it…", "instead", "reschedule", "move"). After a "not available / what time?" reply the pipeline remembers it in the answer cache (`mtg:<chatId>`, 30 min, plus the offered slots), so a bare "12 pm" or "ok" is handled by the template and a time matching exactly one offered slot picks that slot's date (the model had said "12 pm is booked"). The owner gets the first 3 notices of a burst one by one, then one `ownerDigest` (all numbers) after 25 s quiet or 15 items. Tests: `test/burst.test.js`.
- **Availability and clashes (`brain/slots.js`, `brain/availability.js`, migration 005):** free time is never stored as rows, it is derived on demand from working hours (settings `workStart`/`workEnd`/`workDays`, timezone `timezone`) minus **confirmed** appointments (each assumed `meetingMinutes` long, with `meetingBufferMinutes` kept around it) minus the owner's busy blocks (`time_blocks`, console Agenda → Availability). A request overlapping a confirmed meeting or a block, or falling outside hours/days or in the past, is a hard clash (`assess().ok` false); overlapping another *pending* request is a soft clash (accepted, the owner is told). To-dos and date-only items never occupy time. `createAvailability({repo,getSettings})` is shared by the worker (passed to `createBrain`), the gateway and the inbox. In the pipeline's meeting block a hard clash replaces the acknowledgement with `slotTakenAck` ("not available", never says why, plus up to 4 free slots spread over days, intent `meeting_unavailable`; the worker does not file such a request in the Agenda). The owner notice flags clashes (`clashLines`) and offers `force N`; `inbox.decideAgenda` and `PATCH /api/agenda/:id` refuse to confirm a clashing appointment unless forced (WhatsApp: `force 7` / `ok 7 anyway`; console: HTTP 409 → "Confirm anyway?" → `force:true`); a declined appointment tells the contact the free slots; the owner can send `slots` to see free times. `GET /api/agenda` adds `clash` to pending appointments; `GET /api/availability`, `POST/DELETE /api/availability/blocks`. `enforceAvailability:false` turns all of it off. Tests: `test/slots.test.js`.
- **Groq usage counters (`llm/usage.js`):** the console's per-key "Today / 30 days: N calls, tokens" come from Redis hashes `llmusage:<keyId>:<day>` (calls = every attempt incl. 429s, ok, tokens from Groq's usage block, limited, errors; day = the owner's timezone; 45-day TTL) written by `KeyPool.usageSink` in BOTH the worker and the gateway, so they match console.groq.com and survive restarts (the pool's own in-memory counters were per process and reset on every deploy).
- **Language switch:** `statedLanguagePreference` also reads "talk/speak/reply/answer … (to|with me) in <language>", "<language> please/only" and a message that is just the language; an instruction given in the chat always wins over a preference remembered in the notes, and a notes-only preference gives way after two plain-English messages or at once for a clearly English sentence of 4+ words (`replyLanguage`).
- **Groq with several API keys (src/llm/):** setting `llmProvider` has three modes: **`auto`** (default: Groq whenever a key can answer, the local model when every key is used up / Groq is down / no key exists, so adding a key is all it takes), **`ollama`** (local only, Groq never contacted) and **`groq`** (Groq only: the local model is never used; when no key can answer the router throws `GroqUnavailableError`, the worker publishes `{type:'error', error:'llm_busy', busy:true}` and inbox sends the `groqBusyMessage` template ("short break", default `DEFAULT_GROQ_BUSY`, placeholders {name} {persona} {owner}) at most once per 5 min per chat; meeting/pass-on templates and cached answers still work). `groqFallback` is deprecated and ignored. Also `groqModel`. `RoutedLlm` (router.js) is the LLM object the pipeline sees (numCtx, chat, prefill, reusesPrefix, plus `needsLocal()` for the worker's readiness wait) and decides per call: Groq → `GroqClient` (groq.js, OpenAI-compatible SSE) walks a `KeyPool` (key-pool.js): **Groq limits are per model and per organization, so the unit that rests is the (account, model) pair, not the key.** Setting `groqModels` is the model priority list (default gpt-oss-120b, gpt-oss-20b, qwen3.8-27b) and the order of the keys is the account priority. With `groqStrategy: 'priority'` (default) a call tries account 1's models in order, then account 2's models from the top again (its own quotas), then account 3…, then (in `auto`) the local model; `'spread'` lets accounts take turns (least recently used) with models still in order. A 429 rests only that pair until its own retry-after (the **same call immediately continues on the next pair**, no sleep); when the message names the organization (`org_…`) every key of that organization shares the rest, and the console flags such keys ("same organization as account 1: no extra capacity"). 404 "model does not exist / no access" retires that pair for 6 h (that account cannot use the model); 413 (request over the model's per-minute budget) rests the pair 60 s; 401/403 disables the key until the list is reloaded; 5xx/network rests the whole account with a growing backoff; other 400s are not retried elsewhere. Within a strategy a pair whose remaining-token header covers the request is preferred, and a pair whose window is exhausted is rested proactively. Console key order: env keys first, then console keys by `llm_keys.position` (migration 006, ↑/↓ buttons, `POST /api/llm/groq/keys/:id/move`). Usage is also kept per model (`calls:<model>`, `tokens:<model>`). In `auto`, when no key is usable (or Groq fails before the first token) the call falls back to the local Ollama model; a failure after the first token is rethrown (never two models in one reply). Background work (priority >= 3: folds, agenda) stays local while the local model is ready so it never spends Groq quota; think-ahead is skipped for Groq. Two gates: local (`LLM_CONCURRENCY`, priorities) and Groq (`GROQ_CONCURRENCY`, default 32). The router yields a `{type:'meta', provider, model}` event first; the pipeline puts it in the reply meta so the console shows the model that really answered. A request may carry its own provider (the playground: `provider`/`groqModel`, or an explicit local `model`). Keys: `GROQ_API_KEYS` env (read-only in the console) plus keys added in Settings, stored AES-256-GCM encrypted in `llm_keys` (migration 004, key derived from `JWT_SECRET`: rotating it makes stored keys unreadable, they must be re-added); `KeyStore` (key-store.js) rebuilds the pool in both processes on the Redis `ch:llmkeys` message and every minute. The worker heartbeat (`worker:status.llm`) carries live key states; `GET /api/llm/groq` merges them with the key list; `POST /api/llm/groq/keys` verifies a key with `GET /models` before saving, `DELETE /api/llm/groq/keys/:id`, `POST /api/llm/groq/test`, `GET /api/llm/groq/models`. Tests: `test/groq.test.js` (fake Groq server).
- **Cloudflare Workers AI (second hosted provider, `llm/cloudflare.js`):** after Groq and before the local model, in `auto` and in the cloud-only mode (`llmProvider: 'groq'`, labelled "Cloud only"; Groq then Cloudflare, then the break message). It reuses `GroqClient` with another URL (`/accounts/<id>/ai/v1/chat/completions`, OpenAI-compatible) and its own `KeyPool` (ids `cf-env:N` / `cf-db:ID`, `llm_keys.provider='cloudflare'`, `KeyStore` with `idPrefix`). A key is `ACCOUNT_ID:API_TOKEN` (env `CLOUDFLARE_API_KEYS`, or added in Settings; probe = a 1-token completion). Setting `cloudflareModel` (default `@cf/google/gemma-4-26b-a4b-it`, ~560 replies/day; llama-3.1-8b ~400, llama-3.2-3b ~870). **The free tier is 10,000 neurons per account per day, shared by all models, reset 00:00 UTC**; "daily free allocation" (429, code 3036) rests the account until the next 00:00 UTC (`allowanceUsedUp`). Cloudflare sends no usage headers, so neurons are estimated from token counts (`CF_NEURON_RATES`, Redis field `neurons`, kept in hundredths) and the console bar says "estimate". `RoutedLlm` loops over `#tiers` (Groq, Cloudflare); each tier is skipped while all of its pairs rest. Endpoints: `GET /api/llm/cloudflare`, `POST/DELETE /api/llm/cloudflare/keys`, `.../keys/:id/move`, `.../test`. Tests: `test/cloudflare.test.js`.
- **Limit bars (hover or tap the usage bar on an AI account row, `public/js/views/provider-limits.js`; Settings → AI provider is one card: mode switch, one compact row per Groq/Cloudflare account with a ⋯ menu, "Advanced" for models/order/break message):** `KeyPool` keeps, per (account, model), the provider's limit, remaining amount and reset time (`x-ratelimit-limit/remaining/reset-*` headers: Groq requests per day, tokens per minute) plus the limit a 429 named (`limitFromMessage`: "tokens per day, limit 200000, used 199961") and `restUntil`; a window whose reset time passed counts as full again. The panel shows per model a bar, "exhausted", "resets in 2h 14m (at 14:30)".
- **WhatsApp watchdog (`core/watchdog.js`, `WhatsAppManager.#watch`):** while READY, `client.getState()` is probed every 45 s (20 s timeout); a closed page, a hang or a state other than CONNECTED three times in a row drops the browser (killed if `destroy()` hangs for 15 s) and reconnects from the saved session; a browser `disconnected` event does so at once. This replaces the manual Disconnect + Connect after the session went stale while idle.
- **Language instruction and AI log:** `statedLanguagePreference` also understands misspellings ("inglish", "angrezi"), "english bolo / english me baat karo", "speak english" and "hindi mat bolo / don't talk in hinglish" (= English); the final turn carries an explicit rule ("write the whole reply in English, no Hindi words, even if my earlier replies did") because small models copy the language of earlier replies, and "Prefers Hinglish" notes are dropped from the prompt when the person just asked for another language. `RoutedLlm.#served` logs `AI answering: <provider> · <model> · <account>` for every reply and `AI switched: A → B` (with the reason: rate limit, resting, failed) whenever the answering provider/model/account changes.
- **What and how of a meeting (migration 007, `agenda_items.topic/mode/contact_name`):** `agenda.js` `meetingMode` reads the platform or way from the person's own words (Google Meet, Zoom, Microsoft Teams, WebEx, Skype, WhatsApp/phone/video call, in person, online), `meetingTopic` the purpose ("code review", or what follows for/about/regarding/to discuss), `meetingTitle` builds "Code review with Sugam" / "Meet Sugam". They travel in the reply's done-meta `meeting` (with `place`), are stored on the item, shown in the owner notice, the confirmation text (`📝 topic · 💻 mode · 📍 place` via `invite.js detailLine`), the invitation card (What / How·Where rows) and the console (badges, "What for" / "How" fields). A "time please" reply without a platform also asks "Google Meet, a call or in person?". The `place` is only accepted when it comes from the person's words (`placeFromTheirWords`; the model once filed our own "Asli Sumit tak pahuncha diya jayega" as the place). `meetingish` text ("code review on WebEx") is no longer swallowed by the coding intent. Typos: `20tth`, `14 noc 9 0m`, "I wany to meet". When a reply asked for the time, `mtg:<chatId>` keeps `askedDate` so a bare "9 PM" books that day, not today.
- **Agenda survives logging out:** `repo.wipeChatData({agenda})` removes contacts, messages and sessions but keeps `agenda_items` (each item stores `contact_name`) unless `wipeAgenda: true` is sent; the logout dialog says the agenda is kept.
- **Speed (docs/SPEED.md):** one generation at a time (`LLM_CONCURRENCY=1`: parallel generations share the CPU and each runs ~3x slower); background work (agenda, folds) waits `WORKER_BG_QUIET_MS` after the last message; and "think-ahead": after a reply the worker has the model pre-read persona + history (`brain.warm` → `OllamaClient.prefill`, cancelled when a message arrives) so the next reply reads only its own tokens. gemma3 cannot reuse a partial prefix (`reusesPrefix()` is false, think-ahead is skipped); llama/qwen can (−25% to −31% prompt time measured). Setting `prefillAhead`. `warm()` must build exactly the prefix `respond()` sends (tested in `test/prefill.test.js`).
- **One reply per burst:** `core/coalesce.js` (`Coalescer`, used by the worker). Queued jobs of a chat fold into the newest one, which answers everything said since the last reply; a generation that has not sent a bubble yet is aborted and re-run with the new text; once a bubble is out it is never recalled. `brain/repeat.js` makes the pipeline regenerate once (warmer, "say something new") when the first bubble repeats an earlier reply (≥5 words, ≥0.8 word overlap), and inbox drops an identical bubble sent to the same chat within 3 min. Tests: `test/coalesce.test.js`.
- **Owner alerts:** `gateway/llm-monitor.js` probes the LLM every 30 s (`probeLlmStatus` → pure `deriveLlmState`), emits `llm:status`, and after 90 s of "down" (not in the first 5 min after boot) messages the owner's own number once, then once on recovery (`DownAlerter`). `inbox.notifyOwner` sends to `wa.me.wid`; inbound `fromMe` messages are ignored so these never become chat input.
- **Notices to contacts:** session timeout (`timeoutMessage`, from the `end` listener with reason `timeout`) and unreadable media — voice notes, photos, stickers (`unsupportedMessage`, 60 s cooldown per chat, only types in `MEDIA_KINDS`). Both are templates rendered by `renderTemplate` ({name} {persona} {owner} {start} {stop} {kind}).
- **Logging out of WhatsApp** (`POST /api/wa/logout`) only unlinks the phone and deletes the WhatsApp auth session; chats, messages, AI memory notes, sessions and agenda live in this server's Postgres/Redis and used to stay. The console's logout dialog now has a "delete all chats" checkbox (on by default) that sends `wipeData: true`; `inbox.wipeChatData()` then truncates `contacts/messages/sessions/agenda_items` (users, settings, audit log, KB kept), deletes the Redis `ctx:*`, `takeover:*`, `rl:*` keys (`deleteKeysMatching`, SCAN + UNLINK), clears per-chat in-memory state and emits `chats:wiped` so open views refresh.
- **Logs:** go to stdout **and** to a capped Redis list + pub/sub (`core/redis.js` `attachRedisLogSink`). `gateway/realtime.js` relays them to Socket.IO room `logs`. Never log inside that relay handler: it would loop.
- **Own-message echoes:** `core/echo.js` `EchoTracker` recognises the `message_create` echoes of what inbox sends, first by the WhatsApp message id returned from `sendText`/`sendImage` (and any repeat of that id), then by text (counted per chat+text, 30 s) for the race where the event beats `sendMessage`. `WhatsAppManager` also drops duplicate events by message id (`SeenIds`, 10 min) and restarts the client when `ready` fires a second time on the same client (WhatsApp Web reloaded and whatsapp-web.js re-injected its listeners, so every event arrived twice: replies were mistaken for the owner typing and paused the AI); `connect()` has a synchronous `connecting` guard against two Chromiums on one profile. `message_create` events from the phone that aren't ours count as owner takeover (Redis `takeover:<chatId>`, TTL = `takeoverSeconds`, default 30) and are added to memory as assistant turns.

**Web console (`public/`):** vanilla ES modules, no build step, served statically by the gateway.
- The API contract is the routes in `gateway/http.js`. Socket events are `wa:status`, `message:new`, `chat:update`, `typing`, `log` and `model:pull`.
- The CSP is `script-src 'self'`, so no inline scripts.
- Render with the escaping `html` tagged template from `public/js/util.js`. Use `raw()` only for trusted markup.
- `public/js/fx.js` holds library-free ports of the Aceternity effects (Evervault, ContainerScroll, MacbookScroll; FocusCards is the CSS class `.focus-cards`). They write CSS variables once per frame and fall back to a static state under `prefers-reduced-motion`. The Socket.IO client is loaded lazily after sign-in.

**Schema:** `db/migrations/*.sql`, applied in order by `db/pg.js` under an advisory lock (gateway and worker can both boot it). Add new files; never edit applied ones. Rows are mapped to camelCase in `db/repo.js`.

**Deploy:**
- One image with two commands (`docker-compose.yml`). The bus defaults to Redis Streams; Kafka is opt-in (`BUS_DRIVER=kafka` + compose profile `kafka`, ~1 GB RAM).
- CI (`.github/workflows/ci.yml`) runs a boot smoke test with `BUS_DRIVER=redis` and `WA_AUTO_CONNECT=false`.
- `deploy.yml` builds to GHCR and runs `deploy/deploy.sh` over SSH, which health-checks and rolls back.
- The server's `knowledge_base/` is a bind mount seeded once from the image; it is the live source of truth.
